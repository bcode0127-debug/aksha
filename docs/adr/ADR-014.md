# ADR-014: Retry policy

Status: Accepted

Context: `retry_config` defaults to `None`, so nothing retries by default (ADR-013 spike). A blanket retry-all policy would re-run deterministic failures — e.g. a `pydantic.ValidationError` from a malformed LLM output — up to 5 times with backoff climbing to 60s, burning latency and quota on a failure retrying can't fix. The spike also hit a transient `503 UNAVAILABLE` from the model backend on its first run, which a plain re-run resolved immediately — evidence that transient transport failures are real and worth retrying.

Decision: enable `retry_config` only on the two LLM nodes (investigate, explain), with an `exceptions` allowlist limited to transient transport failures and `NodeTimeoutError`. Never retry `ValidationError` — a bad output shape is a deterministic failure that will not change on retry; see TRD §9's fail-fast policy for the malformed-LLM-output path. Function nodes (detect, assemble_explainer_input, file_report) get no `retry_config` — they are deterministic, so a failure there is a bug, not a transient condition.

Consequences: retries stay narrowly scoped to the failure class they can actually fix. Malformed model output fails fast to the `llm_unavailable` fallback instead of being retried, keeping the retry budget (and worst-case latency) predictable.
