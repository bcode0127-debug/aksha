# ADR-016: Detector service gates the triage publish on the conformal threshold

Status: Accepted. Amends TRD v0.4 section 1's pipeline diagram.

Context: TRD v0.4 (locked) documented detector-service as detect -> persist
DetectionResult -> ack -> publish to triage, with no conditional step.
`detector_service.py` implemented exactly that: `score_window()` computes
`is_anomalous` (score >= threshold) and stores it on the DetectionResult, but
`handle_push()` republished every scored window to the `triage` topic
regardless of that field, and `triage_service.py` explicitly excludes
`is_anomalous` from what it forwards into the ADK graph, with no check
anywhere that skips the graph for a non-anomalous window.

Discovered while investigating a replay run (feat/dashboard-scale, PR #29): a
5-minute run over the first 59 rows of the Mission2 test split's chronological
order produced 59/59 incidents (100%), while the offline funnel count over the
same detector and threshold puts the test-split base rate at 3.10%
(5,217/168,410). All 59 incidents' stored score, threshold, and conformal_p
matched the offline recomputation exactly, ruling out a stale artifact or a
differing threshold value -- the gap is architectural, not numerical. The
result: every published window received the full two-Gemini-call agent graph,
not just the ones the detector's own conformal calibration flags, which
undercuts both the cost premise and the funnel narrative the dashboard shows.

Decision: detector-service publishes to the `triage` topic only when
`is_anomalous` is true (score >= threshold). The Firestore `detections` write
(score, threshold, conformal_p) happens for every scored window regardless, so
the funnel's "windows scored" accounting is unaffected. TRD v0.4 section 1's
pipeline diagram is amended to show this as a conditional step.

Consequences: incident volume drops to roughly the detector's calibrated flag
rate (about 3.1% of ingested windows on the Mission2 test split), not 100% of
ingested windows. Existing incidents in Firestore predate this gate and were
not filtered by it; whether to purge and repopulate them is tracked separately
and is not part of this decision. Any doc or dashboard element that assumed
100% of published windows become incidents needs re-checking against this
change.

Measured cost of the ungated replay run (feat/dashboard-scale, PR #29): 59
incidents, 406,234 tokens total, 6,885 tokens per incident, consistent with
the 6,834 to 6,981 tokens per incident range measured separately in
`docs/EVALUATION.md`. Per-incident cost is unchanged by this decision: each
incident that reaches the graph still costs the same two Gemini calls and the
same token range. The entire saving comes from fewer incidents reaching the
graph, not from any incident becoming cheaper.

The size of that saving is a function of the flag rate of whatever is being
ingested, not one headline number. Across the full Mission2 test split the
flag rate is about 3.10% (5,217 of 168,410, `aksha_core/artifacts/mission2_funnel_stats.json`).
Within the rare_event segment at `--start-index=81963` chosen for the demo
replay (`scripts/replay_loader.py`), the flag rate is about 68.3% (41 of 60
rows), measured the same way against the same committed detector. The flag
rate is segment dependent by construction: a demo replay run over a
rare_event-dense period will show a much higher incident rate than the
test-split average, and that difference is expected, not a contradiction of
either number.

This decision has a recall cost, not just a volume saving: see
`docs/EVALUATION.md` section 7 for the 86 of 200 held-out labeled-positive
windows that the verification gate would have correctly confirmed, which do
not survive the conformal threshold this decision now enforces.
